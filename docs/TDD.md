Technical Design Document (TDD): Monopoly Game Engine
Status: Draft | Author: Peter J. Limburg | Co-written with GitHub CoPilot

1. Architectural Overview
We are building a state-based Monopoly engine using Python and FastAPI. The engine follows a Model-Controller pattern to decouple game rules from the API layer.

2. State Machine & Game Phases
To ensure the GameController remains manageable, we will implement a strict GamePhase transition logic:

ROLLING: The player triggers a move.

RESOLVING: The engine identifies the space type (Property, Station, Special).

ACTION_REQUIRED: If the space is unowned, the engine waits for a buy or auction signal.

CLEANUP: Rent is transferred, and the turn is passed.

3. Data Model Constraints
Immutability: The Board structure (40 spaces) is immutable once generated by get_board_spaces.

Ownership Logic: TitleDeed.owner_id acts as the primary foreign key linking properties to the Player list.

Rent Calculation: The calculate_rent method must be context-aware, checking owner_assets to detect monopolies and double the base rent.

4. API Contract (Documentation-First)
The frontend will interact with the engine via these primary endpoints:

POST /game/roll: Triggers dice logic and returns the new space_id.

POST /game/purchase: Finalizes a transaction for the current player on their current space.

GET /game/state: Returns the full JSON of all player positions, balances, and property ownership.
